# T09.3.4 — Spike isolado Authelia + LLDAP

Data: 2026-10-13. Ensaio local e isolado, com usuários, senhas e grupos fictícios. A produção não foi tocada, o
Authelia Green não foi migrado e não houve mudança no Caddy nem nas aplicações.

## Conclusão: **viável**

O LLDAP resolve o bloqueio da T09.3.3. O diretório é um banco transacional consultado pelo Authelia a cada
requisição. Não existe cópia em memória para ficar desatualizada, nem arquivo para regravar, nem janela de supressão.
Nos testes:

- criações, edições, mudanças de grupo, desativações e trocas nativas de senha conviveram **sem nenhuma perda**;
- todas as alterações valeram **na primeira tentativa**, sem espera e sem reiniciar containers;
- o identificador OIDC (`sub`) foi preservado na troca do backend.

Os custos estão em "Riscos". O principal é que as **senhas não migram**: cada usuário precisa definir uma senha nova.

## Ambiente

[tests/lldap-spike/](../tests/lldap-spike/), executado com `tests/lldap-spike/run.sh` (cerca de 2,5 min):

- **Authelia 4.39.28** (mesmo digest da produção) e **LLDAP 0.6.3** (`lldap/lldap@sha256:2a8454b6…`), numa rede Docker
  `--internal`. Segredos aleatórios a cada execução.
- **Configuração** ([config/](../tests/lldap-spike/config/)):
  - `common.yml`: access control (`admin` só para `home-admin`; `app` para `home-admin` e `home-user`), sessão, storage
    SQLite, notifier filesystem e um cliente OIDC fictício;
  - mais `backend-file.yml` (como a produção hoje) **ou** `backend-ldap.yml` (`implementation: lldap`,
    `refresh_interval: always`).
- **Administração pelo caminho de uma futura API:** GraphQL do LLDAP para usuários e grupos, e LDAP Password Modify
  (RFC 3062) como admin para senhas. O harness em .NET 10 usa `System.DirectoryServices.Protocols` sobre `libldap`.
- **Decisões do ensaio:**
  - o LLDAP não tem atributo de conta desativada, então **desativar = entrar no grupo `disabled`**, excluído no
    `users_filter` com `(!(memberOf=cn=disabled,…))`;
  - a conta de serviço `authelia` fica em `lldap_password_manager`, porque o Authelia troca senhas com Password
    Modify usando a conta de serviço (`ldap_user_provider.go`, `setPassword`).

## Preservação dos identificadores OIDC (escopo 7)

O `sub` do OIDC é um UUID opaco gravado pelo Authelia em `user_opaque_identifier`, na chave **(serviço, setor,
username)**, dentro do `db.sqlite3`. Ele não depende do backend. Isso foi comprovado em L1: mesmo `sub` antes e
depois, e nenhuma linha nova.

Para preservá-lo na migração:

1. **Manter o `db.sqlite3`** e a **mesma `STORAGE_ENCRYPTION_KEY`** do Authelia. O storage não é migrado, só o backend.
2. **Usernames idênticos** (o `uid` do LLDAP igual à chave do `users_database.yml`; hoje `diego`). O LLDAP trata ids
   sem diferenciar maiúsculas. Com usernames em minúsculas, que é o caso atual, não há diferença.
3. Os consentimentos OIDC e o restante do storage acompanham o mesmo arquivo. Os clientes OIDC não mudam.

## Backup e recuperação do diretório (escopo 8)

**O que salvar:**

- `/data/users.db` do LLDAP (SQLite);
- os segredos `LLDAP_KEY_SEED` (chave do servidor), `LLDAP_JWT_SECRET` e a senha do admin;
- a senha da conta de serviço do Authelia.

**Backup online, sem parar nada:** `VACUUM INTO '<destino>/users.db'` com qualquer cliente SQLite. No ensaio levou
~31 ms e passou no `PRAGMA integrity_check`.

**Recuperação:** parar o LLDAP, substituir o `users.db` (e apagar `-wal`/`-shm`, se existirem), iniciar o LLDAP. O
Authelia **não é reiniciado**.

| Verificação | Resultado |
| --- | --- |
| Senha vigente no backup, usuários e grupos | ✅ restaurados |
| Usuário criado depois do backup | ✅ ausente (o ponto de restauração vale) |
| Authelia durante a restauração | ✅ não reiniciou (`StartedAt` igual, `restarts=0`) |
| Indisponibilidade | **logins novos falharam por ~3–5 s**; **sessões abertas continuaram com 200** o tempo todo |
| Mesmo backup com **outra `LLDAP_KEY_SEED`** | ❌ bind da alice **recusado**: sem a chave do servidor, nenhuma senha vale |

O backup do Home Server (`infra/home-server-backup`) precisaria incluir o `users.db` (via `VACUUM INTO`) e os
segredos do LLDAP. Isso fica para uma tarefa futura.

## Riscos

| Risco | Observação |
| --- | --- |
| **Senhas não migram** | o LLDAP guarda senhas com OPAQUE, sem importar os hashes argon2 do `users_database.yml`. Cada usuário precisa de uma senha nova na migração (definida pelo admin e trocada depois pelo fluxo nativo). Poucos usuários hoje |
| Novo componente na cadeia de login | com o LLDAP fora, logins novos falham. As sessões abertas continuam, e uma desativação feita nesse intervalo só vale quando o diretório voltar. Também é preciso definir a ordem de partida: **não foi testado** o Authelia iniciando com o LLDAP fora |
| A desativação depende de convenção | é o grupo `disabled` mais o `users_filter`. Um erro no filtro deixa desativados entrarem. O bind LDAP direto do desativado continua funcionando (só importa se outro cliente usar o LLDAP) |
| Chave do servidor | perder a `LLDAP_KEY_SEED` invalida todas as senhas (comprovado). Ela precisa estar no backup de segredos |
| Conta de serviço com poder de troca de senha | `lldap_password_manager` troca a senha de qualquer não-admin. O segredo dela é crítico |
| `refresh_interval: always` | uma consulta LDAP por requisição protegida (no ensaio, forward-auth em ~100–200 ms). Uma alternativa é `1m`, com desativação em até 1 min |
| Sessão perdida após troca de senha | 1 ocorrência em ~190 trocas contínuas, sem causa registrada pelo Authelia. O usuário precisaria entrar de novo. Não afeta a integridade dos dados |
| Exposição | a porta LDAP 3890 (sem TLS) e a interface web/GraphQL 17170 do LLDAP **não podem** ser publicadas fora da rede interna |

O LLDAP também traz uma interface web própria de administração. Usar ou não essa interface é uma decisão para a
tarefa da UI e não foi avaliado aqui.

## Como reproduzir

```sh
tests/lldap-spike/run.sh     # fases 1–4; logs em .tmp/t09.3.4/ (harness, authelia, lldap, probe, run)
```

O script requer Docker. Ele usa a rede só no restore do NuGet do harness, e tudo é removido ao final.
