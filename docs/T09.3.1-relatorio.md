# T09.3.1 — Preparação da administração de usuários do Authelia (backend `file`)

Data: 2026-10-13. Somente diagnóstico e proposta. Nenhum usuário, senha, grupo ou configuração foi alterado.

Fontes:

- código do Authelia v4.39.28 (`internal/authentication/file_user_provider*.go`, `internal/service/file_watcher.go`);
- leitura da produção (só leitura): estrutura do arquivo com salt, hash e e-mail ocultados, `stat` e logs do watcher;
- script existente [scripts/green-test-user.sh](../scripts/green-test-user.sh).

## 1. Estrutura atual

`/srv/accessgateway/data/authelia/users_database.yml` aparece no container como `/data/users_database.yml`.
Dono `root:root`, modo `600`. O diretório `/data` é `root:root 700`, e o `diego` não lê o diretório no host.

```yaml
users:
  diego:
    disabled: false
    displayname: 'Diego'
    password: '$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>'
    groups:
      - 'home-admin'
```

- **Um único usuário, que também é o único `home-admin`.** Um erro hoje bloqueia toda a administração (ver §7).
- Não há `email`. Os grupos que têm efeito são os usados no `access_control`: `home-admin` (todos os hosts) e
  `home-user` (`panel` e `frigate`). Os grupos também vão no claim `groups` do OIDC (HomeAutomation).

## 2. Modelo de dados

Campos do `FileDatabaseUserDetailsModel` (4.39.28) que a ferramenta deve controlar:

| Campo | Obrigatório | Regra proposta |
| --- | --- | --- |
| chave (username) | sim | `^[a-z][a-z0-9._-]{1,31}$`, imutável depois de criado (a busca não diferencia maiúsculas só se configurada; aqui não está) |
| `password` | sim | digest PHC `$argon2id$v=19$m=65536,t=3,p=4$…`; um digest inválido derruba a carga do arquivo inteiro |
| `displayname` | sim | 1–64 caracteres, sem quebra de linha |
| `email` | não | opcional agora; necessário para um futuro SMTP; único entre usuários |
| `groups` | não | só da lista permitida `home-admin`, `home-user`; sem duplicatas |
| `disabled` | não | `true` bloqueia login e, com `refresh_interval` padrão (`always` no backend file), também as sessões já abertas |

Os demais atributos (`given_name`, `address`, `extra`, …) ficam **fora do escopo**. Se aparecerem no arquivo, a
ferramenta recusa a escrita em vez de descartá-los.

DTO da futura API (nunca expõe o hash): `{ username, displayName, email?, groups[], disabled }`.

## 3. Hash Argon2 compatível

- Configuração atual: `password.algorithm: argon2` com os padrões, que geram `argon2id`, `m=65536` KiB, `t=3`, `p=4`,
  chave de 32 bytes, salt de 16 bytes, no formato PHC com base64 sem padding. Na verificação, o Authelia lê os
  parâmetros do próprio digest, então só a variante e o formato precisam ser compatíveis.
- **Na API (.NET):** gerar o hash em processo, com uma biblioteca Argon2 que produza o formato PHC (a escolher na
  T09.3.2). A senha nunca vai para linha de comando.
- **Não usar** `docker exec … authelia crypto hash generate argon2 --password …`, porque a senha apareceria em argv e
  no `ps`. A forma `--random`, usada no `green-test-user.sh`, serve para scripts.
- **Teste de contrato obrigatório:** um digest gerado pelo .NET com uma senha fictícia precisa ser aceito pelo
  `authelia crypto hash validate` da imagem fixada (`docker run --network none`), como no `validate-local.sh`.

## 4. Operações e como não corromper o arquivo

Operações mínimas: **listar**, **criar** (senha aleatória mostrada uma vez), **editar** (`displayname`, `email`,
`groups`), **desativar/reativar** e **redefinir senha** (admin define uma senha temporária).

**Excluir fica fora do MVP.** O `db.sqlite3` guarda dados por username (consentimentos OIDC, 2FA), e recriar o mesmo
nome herdaria esses dados. Desativar resolve o caso comum.

O que pode corromper ou perder alterações, segundo o código:

1. **O Authelia regrava o arquivo inteiro a partir da memória** quando alguém troca a própria senha
   (`ChangePassword` → `Save` → `os.WriteFile`). Se a edição externa ainda não foi recarregada, ela é **apagada sem
   aviso**. A gravação dele também não é atômica: trunca e escreve. Um leitor pode ver o arquivo vazio ou pela metade.
2. **Cooldown de 0,5 s:** depois de cada reload ou save, o Authelia ignora eventos por 0,5 s
   (`ErrWatcherCooldown`, só log debug). Uma edição que cai nessa janela não é carregada.
3. **Arquivo inválido:** o reload falha e o Authelia continua com os dados antigos em memória (erro no log). Mas no
   próximo restart **o Authelia não sobe e o gateway inteiro para**. O próximo save do Authelia também sobrescreve o
   arquivo inválido com a versão antiga.
4. O Authelia só tem lock dentro do próprio processo. Não há como coordenar com ele por `flock`.

Procedimento de escrita proposto (biblioteca única, usada pela API e por scripts):

1. `flock` em `/data/.users_database.lock` (serializa as ferramentas nossas; o Authelia o ignora).
2. Ler os bytes e guardar o `sha256` (H0). Arquivo vazio ou inválido → esperar 200 ms e tentar de novo (pode ser uma
   escrita do Authelia em andamento). Persistindo, abortar.
3. Desserializar, aplicar a operação, validar campos (§2) e invariantes (§7). Serializar e **desserializar de novo**
   para validar o resultado, incluindo a decodificação de todos os digests.
4. Gravar uma cópia do original em `/data/users-history/` (`600`, retenção de 10 versões) para rollback.
5. Criar um temporário **no mesmo diretório** (`.users_database.yml.tmp-*`, `600`), `fsync`.
6. Reler o arquivo atual: se o hash ≠ H0, abortar com conflito (o Authelia ou outra pessoa gravou nesse meio-tempo).
7. `rename` para `users_database.yml`, `fsync` do diretório.
8. Esperar ~1 s (fora do cooldown) e conferir que o hash continua igual ao gravado. Fazer um segundo `rename`
   idêntico para garantir um reload fora da janela de cooldown (a validar no ensaio, T09.3.3).

O risco que sobra é uma troca de senha pelo próprio usuário entre o passo 6 e o reload, uma janela de
milissegundos. O passo 8 detecta isso se o Authelia já tiver regravado o arquivo.

## 5. Permissões, dono e escrita atômica

- `rename(2)` no mesmo diretório é atômico. O `/data` é um bind mount **de diretório**, então o rename feito por
  outro container no mesmo diretório do host é visto pelo Authelia (mesmo inode do diretório). Isso não valeria se
  apenas o arquivo estivesse montado.
- Dono e modo: o arquivo novo nasce do processo que o cria. A API precisa rodar como **root** no container, como o
  Authelia, criar o arquivo com `umask 077` e verificar `root:root 600` antes do rename. Com `cap_drop: [ALL]`, root
  continua escrevendo arquivos dele. Assim não é preciso mudar o uid do Authelia nem as permissões do diretório.
- Montar **só** `/srv/accessgateway/data/authelia` na API. Ela não precisa de `/secrets` nem do socket do Docker.
- `data/authelia` já está no backup (`backup-coverage-check.sh`). O `users-history/` entra junto e tem a mesma
  sensibilidade do arquivo original, porque contém hashes.

## 6. Como o `watch: true` reconhece alterações

O `fsnotify` observa o **diretório** `/data` e filtra pelo nome `users_database.yml`. Eventos `WRITE` ou `CREATE`
disparam `Reload()`. O `rename` de um temporário gera `IN_MOVED_TO`, que o fsnotify trata como `CREATE`. Outros
arquivos do diretório (temporários, `users-history/`, lock) são ignorados.

Confirmado em produção: `09:18:18 Reloaded successfully … op=CREATE` em 11/10, o `mv` do
`green-test-user.sh remove`. Sucesso aparece no log `info`. Falha aparece como `error` ("Error occurred during
reload"). Cooldown e arquivo vazio só aparecem em `debug`.

O reload troca o mapa de usuários de uma vez (não aplica pela metade). Com `refresh_interval: always`, a mudança de
grupo ou a desativação valem na próxima requisição de cada sessão. Tokens OIDC já emitidos continuam válidos até
expirarem.

## 7. Impedir que o administrador perca o próprio acesso

Regras verificadas no passo 3 de §4, antes de qualquer escrita:

- O usuário autenticado (o `Remote-User` vindo do Authelia) **não pode** desativar a si mesmo, nem tirar o próprio
  `home-admin`, nem (no futuro) excluir a si mesmo.
- **Invariante global:** depois da operação, sobra pelo menos **um** usuário `disabled: false` com `home-admin` e
  digest válido. Isso vale também para edições de outros usuários.
- Redefinir a senha de **outro** admin é permitido. A própria senha é trocada pelo fluxo nativo do Authelia (T09.2),
  que confere a senha antiga.
- Saída de emergência: restaurar a última cópia de `users-history/` por SSH. Hoje isso exige ler como root
  (`docker exec`), como no `green-test-user.sh`. A sequência abaixo inclui um script para isso.

Hoje existe **um só** admin. Antes de usar a interface, convém criar um segundo `home-admin`. A decisão é do usuário
e fica fora desta tarefa.

## 8. Integração futura React + ASP.NET Core (sem nova autenticação)

Usar o mesmo padrão dos outros hosts administrativos: **Caddy `forward_auth` → Authelia**.

- Um host novo (por exemplo `users.home.doublesilva.com`) com `import authelia`, mais uma regra `group:home-admin`
  no `access_control`. O SPA React e a API ficam no mesmo host (`/` e `/api/`), sem CORS e sem tokens no navegador.
- A API lê `Remote-User` e `Remote-Groups`, copiados pelo snippet
  [caddy/snippets/authelia.caddy](../caddy/snippets/authelia.caddy), e exige `home-admin` também no código (defesa em
  profundidade).
- A API escuta **só em `127.0.0.1`**, para que só o Caddy chegue nela. O ensaio precisa provar que um `Remote-User`
  forjado pelo cliente é descartado pelo Caddy.
- Mutações só com `POST`/`PUT` em JSON e conferência do `Origin`. O cookie do Authelia é `SameSite=Lax`.
- Alternativa descartada para agora: registrar um cliente OIDC novo, como o `homeautomation-panel`. Isso exige mudar
  a configuração do Authelia e a paridade, e a API passa a validar JWT, o que dá mais trabalho sem ganho para um
  único host.

## Riscos

| Risco | Mitigação |
| --- | --- |
| O Authelia sobrescreve uma edição externa (save a partir da memória) | conferência de hash antes e depois do rename; janela residual pequena |
| Edição ignorada pelo cooldown de 0,5 s | espera de ~1 s e segundo rename idempotente; validar no ensaio |
| Arquivo inválido derruba o Authelia no próximo restart | validação completa antes do rename, digests incluídos; cópia em `users-history/` |
| Perda do único admin | invariantes de §7; segundo admin antes do uso; restauração por SSH |
| A API roda como root com escrita em `data/authelia` | montar só esse diretório, `cap_drop: ALL`, rootfs somente leitura, escuta em loopback |
| Header `Remote-User` forjado | API só em loopback; teste de header forjado no ensaio do Caddy |
| Usuários novos não conseguem trocar a própria senha sem ajuda (o código de elevação vai para um arquivo no servidor, T09.2) | aceitar por enquanto (o admin lê o código); SMTP é tarefa futura |
| Hash .NET incompatível | teste de contrato com `authelia crypto hash validate` da imagem fixada |
