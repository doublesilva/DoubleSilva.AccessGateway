# T07.6.1 — Correção da exposição administrativa do Uptime Kuma

**Data:** 2026-10-13 · **Branch:** `release/t04-cutover` · **Prioridade:** P0 · **Situação:** preparada e testada em
ambiente isolado. **Nada foi aplicado em produção.**

**Resultado:** a correção tem duas camadas independentes, cada uma suficiente para fechar o S1 da T07.6:

1. **Autenticação própria do Kuma religada** pelos mecanismos suportados da versão instalada:
   `extra/reset-password.js`, seguido do evento `setSettings(disableAuth=false)`, que é o mesmo do botão "Enable
   Auth" da interface. Nenhum campo SQLite é alterado à mão. Script: `infra/uptime-kuma/kuma-auth.sh`
   (`--check`/`--apply`/`--rollback`/`--restore-db`), com rollback automático.
2. **Alias `kuma.home` reduzido ao push:** só `GET`/`POST /api/push/<token>` chega ao Kuma, e todo o resto vai por
   301 para `kuma.home.doublesilva.com` (`forward_auth home-admin`). Não é um `forward_auth` no gateway inteiro: o
   push dos monitores continua sem login interativo.

**Achado durante os testes:** a primeira versão do alias, só com `path_regexp`, podia ser **contornada**.
`/socket.io/../api/push/x?EIO=4&transport=polling` casava com o padrão, porque o Caddy normaliza o caminho para o
match, e chegava **cru** ao engine.io do Kuma: o teste recebeu um handshake `{"sid":…}`. Com `disableAuth=true`, isso
seria acesso administrativo. A regra final exige que o caminho cru também seja exatamente `/api/push/<token>`. O
contorno virou teste de regressão no e2e, no `validate-green` e no verificador de contrato.

Testes: sandbox do Kuma **35/35**, e2e (Caddy + Authelia de teste + Kuma) **29/29**, `validate-green` contra as regras
novas **40/0**, `caddy-reload` **35/35** e suíte completa do `validate-local` **63 PASS / 0 FAIL** (smoke 98/98, cutover 64/64, ShellCheck, Gitleaks).

## Etapa A — Diagnóstico

Fontes: código da própria imagem em produção (`docker exec uptime-kuma`, somente leitura), banco em modo
`-readonly` e inventário de rede do host. Nenhum token foi consultado: o único teste sobre eles é um **predicado de
charset** que só devolve contagens (§A.4).

### A.1 Versão e mecanismos de autenticação

| Item | Valor |
| --- | --- |
| Versão | Uptime Kuma **2.5.4**, imagem `louislam/uptime-kuma@sha256:917318f9d7be…` (tag `:2`), Node 22.22.3, SQLite |
| Login | usuário + senha (bcrypt), via Socket.IO (`login`). Limite global de 20 tentativas por minuto |
| 2FA | TOTP opcional (desligado). Remoção oficial: `extra/remove-2fa.js` |
| Sessão "lembrar" | JWT `{username, h}` assinado com `jwtSecret`, **sem expiração**. `h` = shake256 do hash da senha, então **trocar a senha invalida todos os tokens** (`loginByToken` confere `h`) |
| HTTP | `/metrics` com basic auth do usuário, ou API key se `apiKeysEnabled`. **Com `disableAuth=true`, `/metrics` fica aberto** |
| `disableAuth=true` | ao conectar, o servidor faz `afterLogin(socket, primeiro usuário)` e emite `autoLogin`: **qualquer conexão Socket.IO é administradora** |
| SSO / cabeçalho confiável | não existe no Kuma (o `forward_auth` do Authelia é só uma camada externa) |

### A.2 Como o `disableAuth` foi ligado e como reverter de forma suportada

- O `disableAuth` só é ligado pela interface (Configurações → Segurança → "Disable Auth"), e o servidor exige a
  senha atual (`doubleCheckPassword`), ou por escrita direta no banco. A data não é registrada. O mais provável é
  que tenha sido ligado quando o Kuma passou a ficar atrás do `forward_auth` da Blue, sem considerar o alias
  `kuma.home`, que ficou sem autenticação.
- **Reversão suportada:** o botão "Enable Auth" emite `setSettings` com `disableAuth=false`. O servidor não pede
  senha nesse sentido e **desconecta todos os demais clientes** (`disconnectAllSocketClients`, correção
  GHSA-23q2-5gf8-gjpp). O `kuma-auth.js` faz exatamente esse caminho com o `socket.io-client` do próprio container.
- **Senha conhecida antes de religar:** a senha atual do único usuário não é conhecida com segurança. A ferramenta
  oficial `extra/reset-password.js` define uma nova, gira o `jwtSecret` no banco e desconecta os clientes. Ela aceita
  `--new-password`, mas isso poria a senha em argv e no histórico, então o script conversa com os prompts por um
  coprocesso, e a senha vai só pelo stdin.

### A.4 Endpoints

| Tipo | Endpoints | Política no alias |
| --- | --- | --- |
| Administrativos | **Socket.IO** (`/socket.io/`): tudo da interface (monitores, notificações, configurações, tokens). `/metrics` | 301 |
| Push (sem login, pelo token) | `ALL /api/push/:pushToken` → `{"ok":true}` ou 404 `{"ok":false,"msg":"Monitor not found or not active."}` | **proxy** (`GET`/`POST`) |
| Públicos por desenho | `/api/badge/*` (só monitores em status page pública: não há nenhuma), `/status/*`, `/api/status-page/*` (0 páginas), `/upload/*`, `/api/entry-page`, `/robots.txt`, SPA (`*`) | 301 |
| Desenvolvimento | `/test-webhook`, `/_e2e/*`: só com `isDev` (falso na imagem) | 301 |

Consumidores do push: `home-smoke-publish` usa `https://kuma.home/api/push/<token>` (pelo gateway, TLS verificado) e
`backup-home-server` usa `http://127.0.0.1:3001` (fora do gateway). Os tokens são gerados por `genSecret(32)`, só com
letras e dígitos. O `kuma-auth.sh --check` confere, **sem ler o valor**, que os tokens ativos cabem no charset do
alias (`[A-Za-z0-9_-]`): é a trava da fase do Caddy.

### A.5 Conta administrativa e recuperação

1 usuário, ativo, 2FA desligado. A recuperação oficial é `docker exec -it uptime-kuma node extra/reset-password.js`.
Ela invalida as sessões e não mexe em monitores, notificações, histórico ou tokens. Procedimento em §D.7.

### A.6 O que exige autenticação

Tudo, exceto `/api/push/<token>`, que já é protegido pelo próprio token. No alias, só o push passa. No host
autenticado passam o Authelia (`home-admin`) e depois o login do Kuma.

## Etapa B — Arquitetura escolhida

```text
LAN / Tailscale ──► Caddy (Green)
   kuma.home ─┬─ GET|POST /api/push/<token> (caminho normalizado E cru) ──► Kuma :3001 (push)
              └─ qualquer outro ──► 301 https://kuma.home.doublesilva.com{uri}
   kuma.home.doublesilva.com ──► forward_auth (Authelia, home-admin) ──► Kuma :3001 ──► login do Kuma
Host: 127.0.0.1:3001 / 172.20.0.2:3001 ──► login do Kuma (o push local do backup segue igual)
```

| Requisito | Como |
| --- | --- |
| B.1 Autenticação do Kuma | `kuma-auth.sh --apply`: snapshot → senha (2×, sem eco) → `reset-password.js` → Enable Auth → verificação |
| B.2 Proteção adicional via Authelia | mantida no host autenticado. Mais um `forward_auth` no alias quebraria o push, então o alias redireciona para ele |
| B.3 Push preservado com regra restrita | método `GET`/`POST` **e** `path_regexp` (normalizado) **e** `expression` sobre `{http.request.uri.path}` (cru), os dois `^/api/push/[A-Za-z0-9_-]+$` |
| B.4 Sem contorno direto | alias fechado. Host autenticado com `forward_auth`. Acesso pelo host (porta e IP do container) exige o login do Kuma |
| B.5 Nada sensível sem autenticação | `/metrics`, badges e status pages fora do alias. Token inválido recebe só o 404 genérico |
| B.6 Rollback | `--rollback` (Enable → Disable com a senha), `--restore-db <snapshot>` (banco consistente) e `caddy-reload.sh --revert` |
| B.7 Preservação | impressão digital antes e depois (contagens + hashes truncados calculados no container): monitores, ativos, notificação, associações, tokens de push, usuário. Histórico: `heartbeat_max` não diminui |

### Diff exato — `caddy/sites/local-home.caddy`

```diff
 # Paridade com a Blue: estes aliases não passam pelo Authelia (achado de segurança registrado no inventário).
+# Exceção: kuma.home (T07.6.1, fora da paridade).

+# T07.6.1: o alias só entrega o push dos monitores (home-smoke-publish usa https://kuma.home/api/push/<token>).
+# Interface, Socket.IO, /metrics, badges e status pages → 301 para kuma.home.doublesilva.com (forward_auth home-admin).
 kuma.home {
 	tls internal

-	reverse_proxy 127.0.0.1:3001
+	# path_regexp casa com o caminho NORMALIZADO, mas o upstream recebe o caminho CRU: "/socket.io/../api/push/x" casaria
+	# e chegaria ao engine.io do Kuma (handshake administrativo). Por isso o caminho cru também tem de ser exatamente
+	# /api/push/<token>, com um charset sem ".", "%" ou "/" (tokens do Kuma são alfanuméricos).
+	@push {
+		method GET POST
+		path_regexp ^/api/push/[A-Za-z0-9_-]+$
+		expression {http.request.uri.path}.matches("^/api/push/[A-Za-z0-9_-]+$")
+	}
+
+	handle @push {
+		reverse_proxy 127.0.0.1:3001
+	}
+
+	handle {
+		redir https://kuma.home.doublesilva.com{uri} permanent
+	}
 }
```

### D.6 — Critérios objetivos de rollback

| Sinal | Ação |
| --- | --- |
| `kuma-auth.sh --apply` falha depois de habilitar | **automático** (volta a `disableAuth=true`). Investigar antes de tentar de novo; fase 3 não é executada |
| Contagens ou hashes do Kuma diferentes / histórico perdido / monitores sumidos | `kuma-auth.sh --restore-db /srv/accessgateway/backups/kuma-auth-<data>` (para o Kuma ~1 min) |
| Operador sem acesso ao Kuma depois do apply | **não é rollback:** recuperação §D.7 |
| `caddy-reload --apply` reprova (Caddy reiniciado, auth ≠ 200, Green sem 80/443) | `caddy-reload.sh --revert <arquivo indicado>` |
| Push do smoke sem chegar (AVISO no journal ou heartbeat do monitor parado > 10 min) | `caddy-reload.sh --revert …` (o alias volta ao proxy de tudo) e conferir o charset do token |
| `validate-green`: FAIL em qualquer linha que não seja do `kuma.home` | `caddy-reload.sh --revert …` |
| Smoke diferente de 37/0 por causa atribuível à mudança | revert do Caddy. Se persistir, `kuma-auth.sh --rollback` |

`kuma-auth.sh --rollback` reabre a exposição. Só deve ser usado se a autenticação do Kuma causar um problema que o
revert do Caddy não resolva. Para tornar o revert do Caddy permanente, restaure `caddy/sites/local-home.caddy` da
release anterior (`fa0242e`).

### D.7 — Recuperação se o administrador perder o acesso

```sh
sudo docker exec -it uptime-kuma node extra/reset-password.js     # pede a senha nova 2× (os prompts ecoam: tela privada)
# com 2FA ligado no futuro: sudo docker exec -it uptime-kuma node extra/remove-2fa.js
```

A recuperação não para o Kuma nem toca em monitores, notificações, histórico ou tokens, e invalida as sessões
existentes. O acesso continua a passar pelo Authelia (`home-admin`). Sem o Authelia, o caminho é um túnel SSH para
`127.0.0.1:3001`.

### D.8 — Impacto e riscos

| Risco | Prob. | Impacto | Mitigação |
| --- | --- | --- | --- |
| Push do smoke quebrar no alias (token fora do charset) | muito baixa (tokens alfanuméricos) | monitor do smoke DOWN em ≤10 min | predicado do `--check`. Verificação de 2 ciclos. Revert imediato |
| Senha nova perdida | baixa | sem acesso à interface (monitoramento segue) | gerenciador de senhas antes do apply. §D.7 |
| `jwtSecret` girado no banco enquanto o processo usa o antigo em memória | certa | tokens de "lembrar" emitidos agora caem no próximo restart do Kuma (novo login) | nenhum (efeito desejável) |
| Login duplo (Authelia + Kuma) | certa | conveniência | aceito: defesa em profundidade |
| Restore do banco | só em rollback | Kuma parado ~1 min. Perde heartbeats posteriores ao snapshot | só com sinais da §D.6 |
