# T09.1 — Diagnóstico: alteração de senha no Authelia

Data: 2026-10-13. Somente diagnóstico: leituras no repositório, no código-fonte do Authelia v4.39.28 e no container de
produção (somente leitura). Nada foi alterado.

## 1. Backend de usuários

- Backend **file**: `authentication_backend.file.path: /data/users_database.yml`, `watch: true`, hash `argon2`
  ([authelia/configuration.yml](../authelia/configuration.yml), linhas 16–25).
- Produção confere com o repositório: o `sha256` de `/config/configuration.yml` no container `accessgateway-authelia`
  é igual ao do arquivo versionado (`0cf2f397…f547`); imagem `authelia/authelia@sha256:bd97cff4…` = **v4.39.28**.
- `/data` montado **rw** (`/srv/accessgateway/data/authelia`), processo como root, arquivo `600` → o Authelia consegue
  regravar o `users_database.yml`. Usuário existente: `diego`.

## 2. Configurações relacionadas

| Chave | Valor | Efeito |
| --- | --- | --- |
| `authentication_backend.password_reset.disable` | `true` | desliga só o **reset** ("Redefinir senha?" na tela de login); não afeta a alteração |
| `authentication_backend.password_change.disable` | ausente → padrão `false` | alteração **habilitada** |
| `identity_validation.elevated_session` | ausente → padrões | exige código de uso único para alterar a senha |
| `notifier` | `filesystem` → `/data/notification.txt` | o código de elevação é gravado nesse arquivo, não enviado por e-mail |

## 3. Suporte do Authelia 4.39.28

- O backend file suporta alteração de senha nativamente (Configurações → Segurança → "Mudar a senha"). A rota
  `POST /api/change-password` é registrada sempre que `password_change.disable` é `false`, que é o nosso caso
  (`internal/server/handlers.go`, linha 273).
- O botão fica desabilitado, com a dica "Isto está desativado pelo seu administrador", em **dois** casos
  (`web/src/views/Settings/Security/SecurityView.tsx`, linhas 34 e 40):
  `disabled={!configuration || configuration.password_change_disabled}`.
  1. `password_change_disabled = true`. **Não é o nosso caso**: o servidor copia o valor da configuração, que é `false`.
  2. **`configuration` indefinida**: a chamada `GET /api/configuration` falhou. Essa rota exige sessão 1FA válida
     (`middleware1FA`, linha 223). Com a sessão expirada, ela responde 403, e o botão aparece desabilitado com a
     mesma mensagem de "desativado pelo administrador".

## Causa

A configuração **não** desabilita a alteração de senha. O botão aparece desabilitado porque a página de configurações
foi carregada sem sessão válida. Nesse caso, o `GET /api/configuration` falha e a interface mostra o botão desabilitado
(a mensagem atribui isso ao administrador, o que é enganoso). Isso bate com os 403 por sessão expirada já identificados.
Não investiguei esses erros e não mexi no Caddy.

## Solução mínima

1. **Sem mudança de arquivo.** Fazer login de novo em `https://auth.home.doublesilva.com` e recarregar
   Configurações → Segurança. O botão deve ficar habilitado.
2. **Um obstáculo depois do botão:** a alteração exige sessão elevada. O Authelia gera um código de uso único e o
   entrega pelo notifier. Como o notifier é `filesystem`, o código vai para `/data/notification.txt` no servidor
   (`/srv/accessgateway/data/authelia/notification.txt`), e não para um e-mail. Usuários sem segundo fator não podem
   pular esse código (pela documentação de `elevated_session`). Para o uso atual (um único usuário, `diego`), basta
   ler o código nesse arquivo. Para outros usuários, seria preciso um notifier SMTP. Isso é uma decisão separada e
   não faz parte desta solução mínima.
3. **Opcional (documentação):** declarar o padrão em [authelia/configuration.yml](../authelia/configuration.yml) para
   deixar explícito que a alteração é intencional:

   ```yaml
   authentication_backend:
     password_change:
       disable: false
   ```

   Isso não muda o comportamento e tem um custo: `tests/tools/authelia_parity.py` compara a Green com a Blue linha
   a linha e só aceita as trocas `/config → /data`, então as linhas novas fazem o teste falhar. Seria preciso permitir
   a diferença no teste ou mudar o baseline da Blue. **Não recomendado agora.**

## Arquivos que precisariam ser alterados

- Para habilitar: **nenhum**.
- Só se o passo opcional 3 for adotado: `authelia/configuration.yml` + `tests/tools/authelia_parity.py` (ou
  `tests/baseline/blue-configuration.redacted.yml`), seguido do deploy normal da Green.
