# T07.9.1 — Pipeline de release do AccessGateway

**Data:** 2026-10-13 · **Natureza:** diagnóstico e testes locais. Nenhum workflow criado, nenhum deploy, produção
inalterada.

**Resultado:** o repositório gera e valida releases **sozinho**, sem arquivos de HomeAutomation ou Jarvis. As releases
são **reprodutíveis** a partir do commit, e o manifesto de integridade é conferido na instalação. **Não há CI**: testes,
build e instalação são manuais e supervisionados, como decidido na T07.1 (§7). Não há problema que bloqueie a migração.
Os pontos fracos reais estão na §8, com correções mínimas opcionais.

## 1. Workflow do GitHub Actions

**Não existe.** O repositório não tem `.github/` nem outro arquivo de pipeline. Isso está em linha com a T07.1 (§7):
deploy supervisionado, sem deploy automático em push, porque o gateway é ponto único de falha. O CI foi registrado ali
como recomendação, não como requisito.

## 2. Build e empacotamento (`scripts/build-release.sh [commit] [saída]`)

| Aspecto | Como é feito |
| --- | --- |
| Origem | `git archive` **do commit**, não da árvore de trabalho. Árvore suja gera só um AVISO, e as mudanças não entram |
| Fim de linha | `core.autocrlf=false`/`eol=lf` no `archive` (a estação usa `autocrlf=true`, sem `.gitattributes`). O build **aborta** se algum arquivo tiver CR |
| Determinismo | `tar --sort=name --mtime=<data do commit> --owner=0 --group=0 --numeric-owner --mode=u+rwX,go+rX,go-w` + `gzip -n -9` (sem timestamp) |
| Saída | `accessgateway-<commit12>.tar.gz` + `.tar.gz.sha256` |

## 3. Manifesto de integridade

| Item | Conteúdo | Quem confere |
| --- | --- | --- |
| `RELEASE.sha256` (dentro do pacote) | sha256 de **todos** os arquivos, menos ele mesmo e o `RELEASE.json`, em ordem `LC_ALL=C` | operador, depois de extrair: `sha256sum -c --quiet RELEASE.sha256`; também o `cutover.sh` |
| `RELEASE.json` | commit, data do commit, número de arquivos, digests das imagens de produção (Caddy, Authelia, Python) | operador (`grep commit`) |
| `.tar.gz.sha256` | sha256 do pacote | operador, antes de extrair (`sha256sum -c`) |

O `.sha256` do pacote viaja com ele (via `scp` da estação). Ele protege contra corrupção, não autentica a origem; a
autenticidade vem do canal SSH e da geração supervisionada. É adequado ao modelo manual.

## 4. Testes executados

Não há execução automática. O `scripts/validate-local.sh` roda manualmente na estação, com Docker e as imagens fixadas
por digest (Caddy, Authelia, Python, ShellCheck, Gitleaks, Uptime Kuma, Ubuntu). Seções:

```text

kumaauth restoredrill lint
```

Último resultado completo: **66 PASS / 0 FAIL** (13/10, commit `32e6aea`). A suíte cobre:

- e2e com Caddy e Authelia reais, OIDC e sessões;
- suítes com dublês de cutover, rollback, smoke e `caddy-reload`;

## 5. Dependências de outros repositórios

**Nenhuma em build ou teste.** O `build-release.sh`, o `validate-local.sh`, `scripts/lib/` e `tests/tools/` não
referenciam caminhos fora do repositório. Tudo o que é de outros projetos está versionado aqui como baseline ou
artefato próprio:

- `tests/baseline/blue.Caddyfile` e a configuração da Blue sem segredos;
- `infra/deploy-homeautomation` e `infra/home-smoke-test`, com originais em `baseline/`.

Em **tempo de execução** no servidor, os scripts consultam caminhos de outros projetos, como contrato: a CA em
`/etc/homeautomation/certs` e `/etc/jarvis/certs`, os segredos OIDC em `/etc/homeautomation/secrets`, o smoke em
`/usr/local/sbin`. Isso não afeta o build.

## 6. Instalação no servidor (procedimento atual)

Manual, pelo operador, com `sudo`, como na T03 (runbook §1), T06.4 e T07.6.1 (§0.2):

```sh
cd /tmp && sha256sum -c accessgateway-<c12>.tar.gz.sha256
sudo bash -c "cd /srv/accessgateway/app && sha256sum -c --quiet RELEASE.sha256"     # release anterior íntegra
sudo tar -xzf accessgateway-<c12>.tar.gz -C /srv/accessgateway/app --no-same-owner \
  --exclude=./authelia --exclude=./compose.yml --exclude=./env                     # o que exige recriação fica de fora
sudo chown -R root:root /srv/accessgateway/app && sudo chmod -R go-w /srv/accessgateway/app
sudo bash -c "cd /srv/accessgateway/app && sha256sum -c --quiet RELEASE.sha256 && grep commit\\\" RELEASE.json"
# depois, o componente: caddy-reload.sh --check/--apply, install.sh --check/--apply etc.
```

A conferência pós-extração também protege os itens excluídos: se `authelia/`, `compose.yml` ou `env/` mudarem numa
release, o `sha256sum -c` falha e obriga o procedimento de recriação.

## 8. Problemas reais e correções mínimas

| # | Problema | Impacto | Correção mínima (opcional) |
| --- | --- | --- | --- |
| P1 | A extração **sobrepõe** o diretório instalado: um arquivo removido numa release futura continuaria no servidor, e o `sha256sum -c` não detecta arquivos a mais | **nenhum hoje**: nenhum arquivo foi removido entre as releases instaladas (`0e4f80f`, `1647fe1`, `5491a4c`, `aef022d`, `d8b7b83`, `6b47c85`, `4368be6`, `3ed1500`, `bf0b95e`, `9909099`, `1446aa7`, `c7fbf5e`, `f48f3e5`, `fa0242e`, `9afd0c6`) e o `32e6aea` | conferir arquivos a mais depois da extração: `sudo bash -c 'cd /srv/accessgateway/app && comm -13 <(cut -c67- RELEASE.sha256 \| sort) <(find . -type f ! -name "RELEASE.*" ! -path "./authelia/*" ! -path ./compose.yml ! -path "./env/*" -printf "%P\n" \| sort)'` (saída vazia = OK) |
| P2 | O `validate-local.sh` testa a **árvore de trabalho**; a release sai do **commit**. Nada amarra o resultado dos testes ao commit empacotado | baixo (o build avisa sobre árvore suja; na prática os testes rodaram em árvore limpa no commit) | rodar o `validate-local.sh` com `git status --porcelain` vazio e registrar o commit testado no relatório da tarefa, como já vem sendo feito |
| P3 | O procedimento de instalação está repetido em vários relatórios, e a lista de `--exclude` é conhecimento manual | baixo (operador supervisionado; a conferência pós-extração pega desvios dos excluídos) | manter o bloco da §6 como referência única. Um `deploy-accessgateway --check/--apply` (T07.1 §7) fica para depois da migração |
| P4 | `kuma-auth.sh`/`.js` e a seção `kumaauth` seguem no repositório e nas releases, fora da arquitetura (SSO exclusivo) | nenhum (não executados por nenhum procedimento) | remover numa limpeza posterior, se decidido |

Nenhuma correção é necessária para concluir a migração Blue → Green.
